# Discovery Report for MMNext POS (Phase A)\n\n## 1. Core Domain Entities Identified in Legacy FusionPOS\n\nThe legacy application uses a Spring XML configuration (`app.config`) to wire a large number of **Value Objects (VOs)**. The most relevant VOs for the new POS system are:\n\n| VO ID | .NET Type | Description | Notes |\n|-------|-----------|-------------|-------|\n| `saleVo` | `business.domain.vo.Sale` | Represents a sales transaction (header). | Has a corresponding view model `vSaleVo` for read‑only queries. |\n| `saleDetailVo` | `business.domain.vo.SaleDetail` | Line‑items of a sale (product, quantity, price). | Also has `vSaleDetailSerialVo` for serial‑number handling. |\n| `saleTempVo` | `business.domain.vo.SaleTemp` | Temporary sales used during live editing. | Used by live‑sale UI components. |\n| `customerVo` | `business.domain.vo.Customer` | Customer master data. | Singleton and non‑singleton versions (`customerVo` / `customerSVo`). |\n| `stockVo` | `business.domain.vo.Stock` | Product / inventory item. | In the new design this will become the **Product** entity. |\n| `supplierVo` | `business.domain.vo.Supplier` | Supplier master data. | May be needed for purchase workflows. |\n| `purchaseVo` | `business.domain.vo.Purchase` | Purchase transaction header. | Not required for the initial sales‑only MVP. |\n| `transactionLogVo` | `business.domain.vo.TransactionLog` | Audit log for all changes. | Useful for future logging/auditing. |\n| `userVo` | `business.domain.vo.User` | Application user (login/registration). | Provides the current user context. |\n| `saleByCategoryVo`, `topTenSaleVo`, `bottomSaleVo` | Reporting VOs | Provide pre‑aggregated sales statistics used by the reporting UI. |\n\nThese VOs are defined as Spring objects and are instantiated at runtime; the source code does not contain explicit class definitions for many of them, but the types are present in the compiled assemblies. For the new MMNext POS we will define clean POCO classes (`Sale`, `Product`, `Customer`, `Invoice`, …) that capture the same data fields needed for the core workflow.\n\n## 2. UI Flow Overview\n\nThe legacy UI follows a classic WinForms Ribbon pattern:\n\n1. **Startup** – `Program.Main` loads `config.xml` (theme, font, language) and starts a self‑hosted Web API (`HttpSelfHostServer`).\n2. **Login/Registration** – `frmLogin` or `frmRegistration` is shown depending on the registration flag.\n3. **Main Application** – `ribbonfrmMain` (inherits `DevExpress.XtraBars.Ribbon.RibbonForm`) provides a ribbon with tabs for *Sales*, *Purchases*, *Inventory*, *Reports*, *Settings*, etc.\n4. **Module Forms** – Each functional area opens its own form (e.g., `frmSalesEdit`, `frmPurchaseEdit`, `frmStock`, `frmCustomerImport`). Most forms inherit from `XtraForm` (DevExpress) and communicate with the backend via the Spring‑wired services.\n5. **Reporting** – Report forms (`rpt*` classes) are generated using `DevExpress.XtraReports`.\n\nAll forms are tightly coupled to the legacy service layer and perform synchronous database calls; there is no explicit use of `async/await`.\n\n## 3. Pain Points & Technical Debt\n\n| Area | Issue | Impact | Suggested Mitigation |\n|------|-------|--------|----------------------|\n| **Target Framework** | Uses .NET Framework 4.5.2 (missing reference assemblies). | Build fails on modern SDKs. | Migrate to .NET 6/7. |\n| **Synchronous DB Access** | Services call MySQL synchronously (blocking UI). | UI freezes during long operations. | Introduce async repository methods (`MySqlConnector`). |\n| **Memory Management** | Many DevExpress controls are not explicitly disposed. | Potential memory leaks over long sessions. | Implement `IDisposable` pattern in all forms and controls; enforce disposal in `Dispose(bool)`. |\n| **Spring Configuration** | Heavy XML‑based DI (Spring.NET). | Hard to understand and refactor. | Replace with built‑in .NET DI (`Microsoft.Extensions.DependencyInjection`). |\n| **Lack of Layer Separation** | UI directly references VO objects and services. | Tight coupling, hard to unit‑test. | Introduce clean Domain, Application, Infrastructure layers as per the new architecture. |\n| **Hard‑coded UI Themes & Fonts** | Themes are set from `config.xml` via DevExpress skin APIs. | Difficult to change at runtime. | Move them to `appsettings.json` and configure via DI. |\n| **No Automated Tests** | No unit or integration tests in repository. | Regression risk. | Add XUnit tests with Moq for services; integration tests for repositories using Docker‑MySQL. |\n| **DevExpress Licensing** | Requires a developer license for build machines. | Build may fail on machines without license. | Use DevExpress Community edition for development; document license steps for production. |\n\n## 4.
